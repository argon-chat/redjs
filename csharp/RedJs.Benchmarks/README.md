# JavaScript engines from C#

[BenchmarkDotNet](https://benchmarkdotnet.org/) comparisons on .NET 10, Windows x64.
All engines run the same scripts and check the expected result before measurement.

| Engine | Package / binding |
| --- | --- |
| redjs / JavaScriptCore | This checkout's C# bindings and pinned native engine |
| ClearScript / V8 | [Microsoft.ClearScript.V8 7.5.1.1](https://www.nuget.org/packages/Microsoft.ClearScript.V8/7.5.1.1) |
| Jint | [Jint 4.17.0](https://www.nuget.org/packages/Jint/4.17.0) |
| YantraJS | [YantraJS.Core 1.2.507](https://www.nuget.org/packages/YantraJS.Core/1.2.507) |
| Jurassic | [Jurassic 3.2.9](https://www.nuget.org/packages/Jurassic/3.2.9) |
| NiL.JS | [NiL.JS 2.6.1725](https://www.nuget.org/packages/NiL.JS/2.6.1725) |

The callback suite also includes **ClearScriptFast**, using `V8FastHostFunction`.
The ordinary ClearScript entry uses a `Func<double, double, double>` host delegate.
They share the same V8 engine, so the other suites include ClearScript once.

## Run

First run [`../../setup.ps1`](../../setup.ps1) to fetch redjs's native inputs.
The [repository README](../../README.md#build-and-try-it) lists the build tools
and the sibling `redcss` requirement.

From this directory:

```powershell
./build.ps1

# Warmed-up execution and calls in both directions.
dotnet run -c Release --no-build -- --filter '*ThroughputBenchmarks*' '*HostCallbackBenchmarks*' --job short

# First engine creation + first evaluation, one invocation per fresh process.
dotnet run -c Release --no-build -- --filter '*ColdStartBenchmarks*'
```

The build script compiles redjs in Release with default features disabled.
No web APIs are installed for these language and interop benchmarks. Native
output lives in `redjs/target/benchmarks/`, separate from the application build.
Use `./build.ps1 -SkipNativeBuild` when only the C# benchmark code has changed.

BenchmarkDotNet writes Markdown, CSV, HTML, and full JSON reports under
`BenchmarkDotNet.Artifacts/results/`. Its normal CLI works here, including
`--list flat`, `--filter`, `--job`, and `--artifacts`.

For a quick correctness check, run the steady-state suites with `--job dry`.
Dry results are only a smoke test. Use the configured job for cold start;
it has five launches, zero warmups, and one measured invocation per process.

## redjs execution modes

Two additional suites compare redjs against itself on the same workloads:

| Method | How the JavaScript runs |
| --- | --- |
| `SourceJit` | A function evaluated from source, then warmed up by BenchmarkDotNet |
| `BytecodeJit` | Recursively generated bytecode, accepted and loaded before measurement, then warmed up with JIT enabled |
| `BytecodeInterpreter` | The same bytecode path with `useJIT=false`; hot interpreter execution |
| `NativeAot` | A precompiled native JavaScript image, loaded before measurement; JIT is disabled by the image loader |

`RedJsExecutionBenchmarks` measures numeric calls, arithmetic, recursion,
objects, and JSON. `RedJsCallbackModesBenchmarks` measures the same 10,000-call
JS to C# loop in each mode. That adds 24 cases. C# uses the normal .NET JIT in
every case; `NativeAot` refers to JavaScript machine code.

Build the AOT library and images with the exact pinned Bun frontend and the
matching full builtin table. The [native-image probe notes](../../redjs/examples/aot/README.md)
describe obtaining that table from the embedder's generator.

```powershell
./build.ps1 -NativeAot -Frontend <pinned-bun.exe> -BuiltinTable <generated-table-directory>
dotnet run -c Release --no-build -- --filter '*RedJsExecutionBenchmarks*' '*RedJsCallbackModesBenchmarks*' --job short
```

Use `-SkipNativeBuild` with those same AOT arguments to reuse the two native
builds while regenerating images from the current benchmark scripts. The
ordinary cross-engine suites still build without the AOT toolchain. To run
only cache/JIT/interpreter cases, filter out the `NativeAot` methods.

Image compilation happens in separate build processes. The generated sources,
IR, images, and provenance manifests stay under `obj/native-images/`; binaries
are copied into the benchmark workers automatically. Each native image is
checked against its source, engine, frontend, builtin table, compiler options,
and SHA-256 before loading. The loader receives the same verified file handle,
opened with read/execute access and write sharing denied.
Workers select their native library through `REDJS_NATIVE_LIBRARY` before the
first engine call. Each mode stays in its own BenchmarkDotNet process.

Bytecode generation, its first acceptance, image loading, and function lookup
are all in setup. The measured operation calls the already loaded, protected
function. A rejected bytecode cache or native image fails setup; these methods
never report source fallback as a successful AOT/cache result. Dynamic `eval`
is deliberately outside these suites because it would not run native AOT code.

## What is measured

| Scenario | Work per invocation | Reported time |
| --- | --- | --- |
| `eval` | Evaluate `6 * 7` from source | Per evaluation, including the engine's normal parsing/cache behavior |
| `cs-to-js` | Call a cached JS function with one numeric argument, read its numeric result | Per C# → JS call |
| `arithmetic` | 10,000 iterations of integer arithmetic | Per complete run |
| `fibonacci` | Recursive `fib(20)` | Per complete run |
| `objects` | Allocate 1,000 records, then read and sum their fields | Per complete run |
| `json` | Build 128 records, stringify, parse, and read them back | Per complete run |
| Host callbacks | 10,000 `hostAdd(sum, 1)` calls from a JS loop | Per JS → C# callback |
| Cold start | Construct the engine and evaluate `6 * 7` once | Per first use in a fresh benchmark process |

[Workloads.cs](Workloads.cs) contains the shared scripts. They use ES5 syntax
and explicit strict mode so every engine can execute the same language subset.
Prepared functions are cached before the timed region. The host-call adapters
live in [Engines.cs](Engines.cs); redjs protects its cached JS function from GC.

Each benchmark case has its own process and engine. BenchmarkDotNet handles
warmup, invocation counts, overhead measurement, statistics, and result
consumption. redjs is the baseline within each scenario: `Ratio = 2` means
twice its elapsed time. First-use measurements include engine initialization
and its first compilation, but exclude starting the benchmark process and
shutting down the engine.

The callback result includes the JS loop and numeric argument/result
conversion. It is an end-to-end embedding cost, rather than an isolated native
call instruction. `OperationsPerInvoke = 10_000` normalizes both time and
managed allocations per callback.

`MemoryDiagnoser` reports **managed allocations only**. Native allocations in
JavaScriptCore and V8 are outside that counter, so a zero there does not mean
zero memory use. Throughput cases reuse their VM; cold-start cases keep every
engine until process exit, because the current redjs prebuilt cannot safely
tear down a context.

ShortRun is useful for a first comparison. For numbers intended for publication,
repeat on an otherwise idle machine and run the steady-state suites without
`--job short` to let BenchmarkDotNet collect its normal measurement set.
